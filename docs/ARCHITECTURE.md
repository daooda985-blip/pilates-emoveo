# Pilates by emoveo — архитектура продукта

Версия документа: 2.0  
Статус: базовая архитектура утверждена; облачный целевой контур спроектирован, но не подключён

## 1. Продуктовая цель

Pilates by emoveo — публичный веб-продукт для инструкторов Pilates с перспективой упаковки в самостоятельное приложение для компьютера и телефона.

Целевая модель утверждена пользователем: облачное хранение с приоритетом масштабирования до полноценной платформы. Серверная база становится главным источником истины; локальные данные и JSON-резервные копии сохраняются как переходный механизм и средства восстановления. Текущая опубликованная версия пока остаётся локальной — облачная инфраструктура ещё не подключена.

## 2. Архитектурные принципы

1. Сначала каркас и основные пользовательские сценарии, затем расширение.
2. Каждый модуль отвечает за ограниченную область продукта.
3. Существующие рабочие функции сохраняются и подключаются постепенно.
9. Сразу проектировать многопользовательскую изоляцию организаций (multi-tenant) и серверные проверки прав.
4. Данные отделены от интерфейса и бизнес-логики.
5. Облачное хранение должно обеспечивать изоляцию организаций, переносимость данных, резервное копирование и понятный экспорт.
6. Новые функции не должны ломать уже работающие сценарии.
7. ИИ и автоматизация — будущие расширения, а не зависимости базовой версии.
8. Не выдавать общие рекомендации за медицинские назначения или клиническую оценку.

## 3. Структура продукта

### Публичная часть
- Главная / описание продукта
- Возможности
- Вход в рабочее пространство
- Справка, политика конфиденциальности и информация о локальном хранении

### Рабочее пространство
1. **Панель управления** — быстрый доступ, последние комплексы и краткие действия.
2. **Планировщик занятий** — создание, просмотр, редактирование и сохранение занятия.
3. **Библиотека упражнений** — каталог, карточки, категории и поиск.
4. **Шаблоны** — повторное использование типовых комплексов.
5. **Клиенты и группы** — будущий модуль, первоначально только каркас.
6. **Расписание** — будущий модуль, первоначально только каркас.
7. **История и аналитика** — будущий модуль, первоначально только каркас.
8. **Настройки** — параметры генерации, интерфейса, хранения и резервного копирования.

## 4. Основные сценарии первой версии

- Пользователь открывает сайт и переходит в рабочее пространство.
- Настраивает продолжительность, уровень, фокус и оборудование.
- Создаёт черновик занятия из трёх обязательных этапов: разминка, основная часть, растяжка.
- Редактирует упражнения: добавляет, заменяет, удаляет и меняет порядок.
- Сохраняет комплекс локально, открывает его позже и удаляет по запросу.
- Ищет упражнение в библиотеке и просматривает его карточку.
- Экспортирует облачные данные в переносимый файл и при необходимости импортирует локальную резервную копию.

## 6. Техническая архитектура

На переходном этапе можно сохранить GitHub Pages для frontend. Для облачного контура рекомендовано рассмотреть Supabase (PostgreSQL, Auth, RLS, Storage, Edge Functions), но поставщик ещё не утверждён и проект не создан. Frontend не должен обращаться к таблицам напрямую: доступ организуется через слой репозиториев/адаптеров.

Целевые слои:

- **UI** — страницы, компоненты, формы и навигация.
- **Application** — сценарии пользователя: создать занятие, сохранить, открыть, экспортировать.
- **Domain** — правила занятия, этапы, упражнения и проверки.
- **Data** — каталог упражнений, шаблоны и пользовательские данные.
- **Infrastructure** — localStorage/IndexedDB, импорт/экспорт и будущие адаптеры.

Целевая структура репозитория (внедряется поэтапно):

```text
/
├── index.html
├── pages/                 # страницы приложения
├── css/                   # токены, базовые стили, компоненты
├── js/
│   ├── core/              # запуск, события, общие утилиты
│   ├── app/               # сценарии приложения
│   ├── domain/            # правила предметной области
│   ├── modules/           # planner, library, settings и др.
│   └── infrastructure/   # локальное хранилище, импорт/экспорт
├── data/                  # каталог упражнений и шаблоны
├── assets/                # изображения, иконки и медиа
└── docs/                  # архитектура, решения и план
```

Это целевая карта, не инструкция сразу переносить все файлы. Текущие файлы index.html, js/generator.v1.js и data/exercise-library.v1.json остаются рабочими до безопасного переноса.

## 7. Модель хранения

### Целевая облачная модель
- Аккаунты пользователей, профили и членство в студиях.
- Клиенты, группы, планы, шаблоны, расписание и посещаемость — с обязательной привязкой к студии.
- Системная библиотека упражнений отделена от пользовательских и студийных данных.
- PostgreSQL — рекомендуемая основа базы; точная схема описана в docs/CLOUD_PLATFORM_DESIGN.md.

### Правила
- Облачная база — главный источник истины после перехода.
- Доступ к каждой записи студии защищается серверными политиками RLS, а не только frontend-фильтрами.
- Секретные ключи не попадают в браузер и репозиторий.
- Локальный экспорт сохраняется для переносимости и восстановления.
- Не переносить реальные данные до готовности аутентификации, RLS, резервного копирования и политики конфиденциальности.

## 8. Границы публичного продукта

Публичный сайт — входная точка продукта. Рабочая платформа рассчитана на облачные аккаунты и несколько устройств. Данные разных студий изолируются на серверной стороне; клиентский вход не включается автоматически в первый облачный релиз.

## 9. Критерии готовности каркаса

- Есть единая навигация и понятная структура разделов.
- Все пункты меню ведут на существующие страницы или явно обозначенные заглушки.
- Планировщик, редактор и библиотека доступны из общей оболочки.
- Основные пользовательские данные сохраняются и восстанавливаются через облачный контур.
- Есть экспорт/импорт пользовательских данных.
- Существующие сценарии генерации и редактирования не потеряны.
- На телефоне интерфейс остаётся пригодным для работы.
- Нет кнопок, которые выглядят рабочими, но ничего не делают.

## 10. Не входит в каркас

- Генерация с помощью сложной ИИ-модели.
- Клиентские кабинеты, платежи и внешние интеграции до отдельных согласований.
- Viber/Telegram и автоматизация посещаемости.
- Медицинская диагностика или обещания лечебного эффекта.
- Полноценная аналитика и автоматические отчёты.
