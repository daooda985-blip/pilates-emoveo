# Pilates by emoveo — проверка бесплатной инфраструктуры и готовность к синхронизации

Дата проверки: 31 октября 2026  
Статус: исследование и проектирование; внешние сервисы не подключены, аккаунты/проекты не создавались.

## 1. Обязательные ограничения

- Бюджет: 0 BYN / 0 USD на текущем этапе.
- Любые расходы возможны только после отдельного явного согласия пользователя.
- Первый production-рынок: Беларусь.
- Реальные персональные данные клиентов не загружать, пока не подтверждены правовые основания, география всех потоков, договоры, безопасность и восстановление.
- Зарубежные бесплатные сервисы допустимы только для прототипов с вымышленными данными, пока не завершена правовая проверка.

## 2. Результат проверки бесплатных облачных вариантов

### GitHub Pages — оставить для frontend

Подходит для бесплатной публикации статического интерфейса. Не предоставляет собственную серверную PostgreSQL, авторизацию пользователей и безопасный backend. Поэтому это текущая бесплатная оболочка, но не готовая облачная платформа.

### Supabase Free — только прототип, не production для реальных клиентских данных

По официальным материалам Supabase:
- Free: до 2 активных проектов, PostgreSQL до 500 MB на проект, 5 GB egress и лимиты по другим ресурсам.
- Free-проекты могут приостанавливаться после недели низкой активности.
- Автоматические ежедневные резервные копии не входят в Free; ручной backup можно выполнять отдельно.
- Платный Pro начинается от 25 USD/месяц; превышения/дополнения могут создавать расходы.

Вывод: полезен для учебного прототипа с синтетическими данными, но не выбран для production. Зарубежное размещение также требует отдельной проверки трансграничных потоков.

Источники:
- https://supabase.com/pricing
- https://supabase.com/docs/guides/platform/free-project-pausing
- https://supabase.com/kb/faqs/platform/free-plan-backups

### Neon Free — только прототип, не production для реальных клиентских данных

По актуальным официальным материалам Neon:
- Free: до 100 проектов, до 1 GB PostgreSQL на проект, 100 CU-hours вычислений на проект в месяц, 5 GB исходящего трафика на проект.
- Вычисления автоматически переходят в режим scale-to-zero после периода бездействия; при исчерпании квоты вычисления приостанавливаются до следующего периода или перехода на платный тариф.
- Это управляемый PostgreSQL, но для полноценной системы нужно отдельно проверить API/backend, авторизацию, резервное копирование, географию и договорные условия.

Вывод: удобный бесплатный стенд для тестов на синтетических данных. Не использовать для production-данных Беларуси без отдельной юридической и технической оценки.

Источники:
- https://neon.com/pricing
- https://neon.com/docs/introduction/plans

### Белорусские варианты

- Cloud.by публично указывает виртуальный хостинг от 5 BYN/месяц, VPS от 12 BYN/месяц и 14-дневный тестовый период без карты. Это не постоянное бесплатное решение; тест не удовлетворяет правилу «только бесплатно».
- Mistedo Cloud показывает почасовую оплату ресурсов и бесплатный тестовый период, но не постоянный бесплатный production-тариф. Сам факт Минского ЦОД не подтверждает географию резервных копий, логов, поддержки и субподрядчиков.

Вывод: среди проверенных вариантов постоянный бесплатный production-хостинг с подтверждённой полной обработкой данных в Беларуси не найден. Это не доказательство, что такого предложения нигде нет; до появления документально подтверждённого варианта production-облако не разворачивать.

Источники:
- https://cloud.by/
- https://mistedo.by/

## 4. Подготовка текущего сайта к будущей синхронизации

Текущая реализация в index.html использует:
- один ключ localStorage: emoveo.pilates.local.v1;
- объект состояния version/settings/plans/templates;
- функции чтения и записи состояния;
- JSON export/import;
- генератор и библиотеку упражнений как отдельные от пользовательских сохранений данные.

Это хорошая отправная точка для постепенного выделения слоя хранения, но сейчас интерфейс обращается к синхронному localStorage. Облачная база работает асинхронно по сети. Нельзя просто заменить localStorage на fetch без переработки сценариев сохранения, загрузки, ошибок и конфликтов.

### Безопасная последовательность

1. Зафиксировать текущий JSON backup v1 как поддерживаемый формат импорта.
2. Ввести единый контракт репозитория: loadState, saveSettings, savePlan, deletePlan, saveTemplate, deleteTemplate, exportBackup, importBackup.
3. Сначала реализовать LocalRepository поверх текущего localStorage, сохранив прежнее поведение и ключ данных.
4. Перевести интерфейсные обработчики на этот контракт и покрыть их проверками.
5. Подготовить CloudRepository как отдельную реализацию, но не включать её в интерфейс до выбора провайдера.
6. Для облачной реализации использовать API/backend и серверную проверку прав; секретные ключи не хранить в браузере.
7. Синхронизацию включать только после Auth, изоляции студий, миграций, резервного копирования, экспорта/восстановления и проверки конфликтов.
8. Импорт локальной резервной копии выполнять через preview → подсчёт → явное подтверждение → отчёт. Никогда не перезаписывать существующие данные молча.

### Обязательные тесты слоя хранения

- Первый запуск без существующего хранилища.
- Чтение существующего формата v1 без потери данных.
- Сохранение и повторное открытие плана/шаблона.
- Ошибка записи и откат состояния интерфейса.
- Некорректный JSON и неизвестная версия.
- Повторный импорт без случайных дублей.
- Большой backup / переполнение localStorage.
- Offline/timeout при будущей облачной реализации.
- Два устройства одновременно меняют одну запись: обнаружение конфликта и выбор пользователя, не last-write-wins без предупреждения.

## 5. Предлагаемые значения для ещё не утверждённых правил доступа

Это рекомендации для обсуждения, а не подтверждённые продуктовые решения:

- Instructor: доступ к клиентам только в назначенных группах и собственным занятиям; администратор может расширить доступ в рамках студии.
- Staff: по умолчанию нет доступа к клиентским заметкам; можно отдельно выдать только операционные права на расписание и отметку посещаемости.
- Клиент может состоять в нескольких группах одновременно; история членства сохраняется через joined_at/left_at.
- Статусы посещаемости: present, absent, cancelled, no_show — оставить как предложено в текущей схеме.
- Срок хранения клиентских карточек, заметок, посещаемости и резервных копий не задавать технически до юридической проверки и определения оператора данных.

Не создавать облачные проекты, не активировать trial, не привязывать карту, не подключать платный тариф, не загружать клиентские данные и не включать синхронизацию без отдельной проверки соответствующих условий. Любое возможное списание требует отдельного согласия пользователя.

## 8. Выполненный первый шаг в коде — storage adapter

31 октября 2026 добавлен файл `js/storage.local.v1.js` и подключён в `index.html` перед основным приложенческим скриптом.

Адаптер:
- сохраняет прежний ключ `emoveo.pilates.local.v1`;
- предоставляет методы `getItem()`, `setItem(value)`, `removeItem()`;
- не меняет формат состояния v1 и JSON backup;
- не отправляет данные в сеть и не подключает облако;
- оставляет текущую синхронную семантику, чтобы не ломать действующие обработчики.

Основной код теперь обращается к `window.PilatesStorageV1`, а не вызывает localStorage напрямую в местах чтения/записи/очистки.

Это только первый адаптерный слой, не полноценный LocalRepository: сериализация, проверка схемы, история и шаблоны пока остаются в основном скрипте. Следующий этап — перенести эти операции в репозиторий, добавить контрактные тесты и только потом рассматривать асинхронный CloudRepository.

Проверено чтением сохранённых файлов GitHub: файл адаптера существует, подключение стоит до основного скрипта, ключ и вызовы совпадают. Полный браузерный регрессионный тест после этого изменения ещё не выполнялся; до такого теста не объявлять рефакторинг полностью проверенным.
