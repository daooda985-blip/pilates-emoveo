# Pilates by emoveo — проект облачной платформы

Версия: 1.1  
Статус: продуктовые правила первого облачного релиза согласованы; инфраструктура не подключена  
Основание: выбор пользователя — модель B (облачная), главный приоритет — масштабирование до полноценной платформы.

## 1. Целевой результат

Перевести Pilates от автономного сайта к облачному продукту для инструкторов и студий. Пользователь входит в аккаунт с разных устройств и получает доступ к своим рабочим данным. В дальнейшем платформа сможет поддерживать несколько студий, инструкторов, клиентские профили, группы, расписание, посещаемость, отчёты и отдельные клиентские кабинеты.

Облачная модель означает, что серверная база становится главным источником истины. Локальный кэш и экспорт остаются вспомогательными средствами, но не заменяют облачное хранение.

## 2. Архитектурная рекомендация

### Предлагаемый стартовый стек

- **Frontend:** сохранить текущий HTML/CSS/JavaScript на первом облачном шаге; не переписывать сайт в новый фреймворк только ради подключения базы.
- **Backend platform:** рассмотреть Supabase как управляемую платформу на PostgreSQL: Auth для входа, PostgreSQL для данных, Row Level Security (RLS) для изоляции данных, Storage для файлов и Edge Functions для серверных операций.
- **Database:** PostgreSQL с миграциями схемы и ограничениями целостности.
- **Hosting:** GitHub Pages можно оставить для публичной оболочки на переходном этапе; приложение обращается к облачному API по HTTPS. Если появятся серверные функции или единый домен, отдельно выбрать хостинг приложения.
- **API boundary:** весь доступ к данным проходит через отдельный слой репозитория/адаптера. UI и генератор не должны напрямую зависеть от конкретного провайдера базы.

Supabase — рекомендация для проектирования, а не уже выбранный и подключённый сервис. Перед регистрацией проекта, включением платного тарифа или переносом реальных данных нужно проверить актуальные условия, регион размещения, лимиты, резервное копирование и требования к защите данных.

## 3. Модель организаций и доступа

Сразу проектировать multi-tenant архитектуру — модель, в которой одна база обслуживает много независимых организаций, но каждая видит только свои записи.

Основные сущности доступа:
- **User** — учётная запись человека, подтверждаемая облачной Auth-системой.
- **Studio** — студия или самостоятельная практика инструктора; у одного пользователя потенциально может быть доступ к нескольким студиям.
- **Membership** — связь пользователя со студией и его роль.
- **Role** — владелец, администратор, инструктор. Роли первого релиза: владелец студии, администратор, инструктор и приглашённый сотрудник. Клиент не имеет собственного аккаунта и не входит в систему. Клиентские карточки ведут сотрудники студии.

Все принадлежащие студии записи получают поле studio_id. Политики RLS проверяют членство пользователя в соответствующей студии на стороне базы. Нельзя полагаться только на скрытие кнопок или фильтрацию данных в интерфейсе.

## 4. Предлагаемая модель данных

| Сущность | Назначение | Основные связи |
|---|---|---|
| profiles | Публичные настройки профиля пользователя | auth.users |
| studios | Студия или практика | владелец, участники |
| studio_memberships | Участие пользователя и роль | user ↔ studio |
| clients | Клиентская карточка: имя, контакт при необходимости, группа | studio |
| client_notes | Рабочие заметки инструктора | client, studio, author |
| groups | Группы занятий | studio |
| group_members | Состав группы | group, client |
| exercises | Системный каталог упражнений | общие записи каталога |
| exercise_versions | Версии карточек упражнений | exercise |
| plans | План/комплекс занятия | studio, author |
| plan_items | Упражнения и порядок внутри этапов | plan, exercise |
| templates | Шаблоны занятий | studio, author |
| schedule_events | Запланированное занятие | studio, instructor, group/clients |
| attendance | Факт посещения | schedule_event, client |
| audit_events | Важные события доступа и изменения данных | studio, actor |

Это концептуальная схема, не готовая SQL-миграция. Точные поля, ограничения и индексы определяются при реализации после проверки сценариев.

## 5. Правила безопасности и приватности

1. В браузере хранить только публичный ключ клиента, предназначенный для безопасного использования с RLS; секретные service-role ключи и пароли не помещать в frontend, репозиторий или публичные файлы.
2. Каждая таблица с данными студии должна иметь studio_id и политики RLS для чтения/создания/изменения/удаления.
3. Серверные административные операции выполнять только в доверенной среде, не из браузера.
4. Проверять права не только при чтении, но и при записи, смене владельца и удалении.
5. Минимизировать данные клиентов: собирать только то, что действительно нужно для работы инструктора.
6. Не превращать заметки инструктора в медицинскую карту; не запрашивать диагнозы и не обещать клиническую оценку. Если позже появится работа с чувствительными данными о здоровье, до этого нужен отдельный юридический и security review.
7. Предусмотреть экспорт данных организации, удаление/закрытие аккаунта, политику хранения и резервное копирование.
8. Не хранить данные платёжных карт самостоятельно; платежи, если появятся, поручать специализированному провайдеру.
9. Вести минимальный журнал важных действий без избыточного копирования содержимого личных заметок.
10. Проверять RLS тестами на двух независимых студиях: пользователь студии A не должен прочитать или изменить данные студии B.

## 6. Переход с текущей локальной версии

Переход выполнять без внезапного удаления текущего локального механизма:

1. Зафиксировать формат текущего JSON backup как источник миграции.
2. Добавить слой repositories / data-adapters: LocalRepository для текущего хранилища и будущий CloudRepository.
3. Добавить экран входа и состояние сессии только после готовности Auth и RLS.
4. Для авторизованного пользователя читать и записывать облачные данные через репозитории.
5. Добавить явный мастер импорта существующего JSON в облачный аккаунт: предварительный просмотр, подсчёт записей, подтверждение, отчёт о пропусках и повторяемость без дублей.
6. Сохранить экспорт облачных данных в переносимом формате.
7. После проверки облачного сценария определить, оставить ли локальный режим как резервный/офлайн режим или убрать его из основного потока.

Не объединять автоматически локальные данные разных браузеров и аккаунтов. При конфликте данных нужен понятный выбор пользователя; молча перезаписывать записи запрещено.

## 8. Критерии допуска к реальным данным

- RLS включён и проверен автоматическими негативными тестами.
- Нет секретных ключей в frontend или публичном репозитории.
- Проверены роли и границы доступа.
- Есть экспорт, резервное копирование и понятный сценарий восстановления.
- Есть политика конфиденциальности и описаны цели/сроки хранения.
- Есть процедура удаления аккаунта и данных.
- Проверены ошибки сети, повторная отправка и конфликты.
- Проведён ручной тест на двух отдельных аккаунтах/студиях.

## 10. Согласованные правила первого облачного релиза

Пользователь подтвердил:
1. В систему входят только инструкторы и сотрудники студии. Клиенты не получают собственные аккаунты и личные кабинеты в первом релизе.
2. Клиентская карточка содержит только минимальные рабочие сведения: имя, контакт при необходимости, группу, посещаемость и нейтральные заметки.
3. Диагнозы, медицинские документы и подробные сведения о здоровье не входят в MVP.

### Следующая точка согласования

До создания облачного проекта нужно утвердить поставщика и регион размещения данных. Supabase/PostgreSQL остаётся рекомендуемым вариантом, но ещё не выбран окончательно. Затем будут подготовлены конкретная схема таблиц, миграции и RLS-тесты.

До готовности Auth, RLS, резервного копирования, политики конфиденциальности и процедуры удаления реальные клиентские данные не подключать.


## 11. Детализация клиентских данных и ролей первого релиза

### Роли

| Роль | Возможности в пределах студии |
|---|---|
| owner | Управление студией, участниками, настройками и всеми рабочими данными студии |
| admin | Управление клиентами, группами, расписанием и сотрудниками в пределах выданных полномочий |
| instructor | Работа со своими занятиями, группами и клиентскими записями в пределах назначенного доступа |
| staff | Ограниченные операционные действия, которые будут определены матрицей разрешений до реализации |

Роль и разрешения проверяются сервером. Скрытие элементов интерфейса не считается защитой. Роль owner должна назначаться только доверенным процессом создания студии/передачи владения, а не обычным клиентским запросом.

### Клиентская карточка MVP

| Поле | Правило |
|---|---|
| display_name | Обязательно; имя для отображения |
| contact | Необязательно; только если нужно для организационной связи |
| group_memberships | Ноль или несколько групп, если это поддержит реальный сценарий |
| attendance | Факт посещения, отмены или отсутствия по согласованным статусам |
| notes | Нейтральные рабочие заметки; не использовать для диагнозов и медицинских документов |

Не добавлять дату рождения, домашний адрес, медицинскую историю, диагнозы, документы и другие поля «на будущее» без отдельного обоснования и согласования.

### Базовые ограничения целостности

- Клиент, группа, событие расписания и посещаемость принадлежат одной студии.
- Нельзя связать клиента одной студии с группой или событием другой студии.
- Участник не может сам повысить себе роль или добавить себя в чужую студию.
- Удаление клиента должно иметь предсказуемую политику для посещаемости и заметок: сначала архивирование/экспорт, затем согласованное удаление или обезличивание.
- Контакт хранится отдельно от заметок и не дублируется в журналах событий.
- Все даты занятий хранятся с однозначной временной зоной/UTC-моментом и отображаются в часовом поясе студии.

### Проверки перед допуском данных

- Тесты на чтение/изменение/удаление между двумя студиями.
- Тесты на попытки подделать studio_id и повысить роль.
- Тесты на связи между сущностями разных студий.
- Тесты на экспорт, удаление, архивирование и восстановление.
- Проверка отсутствия секретов в клиентском коде и Git-истории.


## 12. Решение по географии первого облачного релиза — 31 октября 2026

**Подтверждено пользователем:** первый облачный релиз предназначен только для Беларуси. Другие страны СНГ не подключаются к первому production-контуру. Расширение на другие страны рассматривается отдельным этапом после правовой и технической оценки.

### Предварительное архитектурное решение

- Для production-клиентских данных целевой регион — дата-центр физически в Республике Беларусь.
- Основная PostgreSQL-база, файловое хранилище, журналы с персональными данными и резервные копии должны быть размещены в согласованной белорусской инфраструктуре либо отдельно юридически проверены до использования зарубежного расположения.
- Внешние сервисы (почта, аналитика, мониторинг, CDN, обработка ошибок, резервные копии) не должны получать персональные данные по умолчанию. Для каждого сервиса проверять местонахождение, субподрядчиков, доступ поддержки и условия поручения обработки.
- GitHub Pages остаётся только публичной оболочкой текущего сайта; не помещать туда клиентские данные, приватные документы или секреты.
- Архитектура сохраняет PostgreSQL и адаптерный слой, чтобы позже можно было развернуть отдельные региональные контуры без смешивания данных стран.

### Провайдеры-кандидаты, не утверждены

1. **Белорусский облачный/VPS-провайдер с подтверждённым Минским ЦОД** — предпочтительный класс решения. Кандидаты для запроса технических и договорных условий: Cloud.by, hoster.by, beCloud и другие местные операторы.
2. **Самостоятельный PostgreSQL на VPS/облачной VM в Беларуси** — технически возможен, но требует нашей ответственности за обновления, мониторинг, резервное копирование, восстановление, HA и безопасность.
3. **Supabase в зарубежном регионе** — не выбирать для production с данными белорусских клиентов до отдельного правового заключения и документированной оценки трансграничной передачи. Его удобство Auth/RLS не отменяет требований к обработке данных.

### Что обязательно подтвердить у провайдера письменно

- точный адрес/страна основного ЦОД и всех резервных площадок;
- где физически находятся snapshots, backups, логи, метрики и аварийные копии;
- кто является договорной стороной и кто выступает уполномоченным лицом при обработке данных;
- список субподрядчиков и стран, из которых возможен административный доступ;
- договорные условия конфиденциальности, инцидентов, уведомления, возврата и удаления данных;
- доступность PostgreSQL 16+ или установки собственной версии, сетевые ACL, TLS, шифрование дисков/backup;
- RPO/RTO, SLA, тестирование восстановления и процедура выхода/экспорта;
- оплата, поддержка, ограничения, доступность из Беларуси и порядок прекращения услуг.

### Правовой статус

Это проектные требования и предварительная техническая позиция, а не юридическое заключение. До production необходимо проверить действующую редакцию Закона № 99-З, актуальный перечень государств с надлежащим уровнем защиты, применимость статьи 9 к конкретным поставщикам и их субподрядчикам, а также договор поручения обработки. Не предполагать, что размещение основной базы в Беларуси автоматически исключает трансграничную передачу: зарубежные панели поддержки, телеметрия, CDN, почта и backups также могут передавать персональные данные.
