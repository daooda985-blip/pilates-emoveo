# Pilates by emoveo — проект облачной платформы

Версия: 1.0  
Статус: проектирование; облачная инфраструктура не подключена  
Основание: выбор пользователя — модель B (облачная), главный приоритет — масштабирование до полноценной платформы.

## 1. Целевой результат

Перевести Pilates от автономного сайта к облачному продукту для инструкторов и студий. Пользователь входит в аккаунт с разных устройств и получает доступ к своим рабочим данным. В дальнейшем платформа сможет поддерживать несколько студий, инструкторов, клиентские профили, группы, расписание, посещаемость, отчёты и отдельные клиентские кабинеты.

Облачная модель означает, что серверная база становится главным источником истины. Локальный кэш и экспорт остаются вспомогательными средствами, но не заменяют облачное хранение.

## 2. Архитектурная рекомендация

### Предлагаемый стартовый стек

- **Frontend:** сохранить текущий HTML/CSS/JavaScript на первом облачном шаге; не переписывать сайт в новый фреймворк только ради подключения базы.
- **Backend platform:** рассмотреть Supabase как управляемую платформу на PostgreSQL: Auth для входа, PostgreSQL для данных, Row Level Security (RLS) для изоляции данных, Storage для файлов и Edge Functions для серверных операций.
- **Database:** PostgreSQL с миграциями схемы и ограничениями целостности.
- **Hosting:** GitHub Pages можно оставить для публичной оболочки на переходном этапе; приложение обращается к облачному API по HTTPS. Если появятся серверные функции или единый домен, отдельно выбрать хостинг приложения.
- **API boundary:** весь доступ к данным проходит через отдельный слой репозитория/адаптера. UI и генератор не должны напрямую зависеть от конкретного провайдера базы.

Supabase — рекомендация для проектирования, а не уже выбранный и подключённый сервис. Перед регистрацией проекта, включением платного тарифа или переносом реальных данных нужно проверить актуальные условия, регион размещения, лимиты, резервное копирование и требования к защите данных.

## 3. Модель организаций и доступа

Сразу проектировать multi-tenant архитектуру — модель, в которой одна база обслуживает много независимых организаций, но каждая видит только свои записи.

Основные сущности доступа:
- **User** — учётная запись человека, подтверждаемая облачной Auth-системой.
- **Studio** — студия или самостоятельная практика инструктора; у одного пользователя потенциально может быть доступ к нескольким студиям.
- **Membership** — связь пользователя со студией и его роль.
- **Role** — владелец, администратор, инструктор. Роль клиента и клиентский вход не включать в первый рабочий релиз без отдельного решения.

Все принадлежащие студии записи получают поле studio_id. Политики RLS проверяют членство пользователя в соответствующей студии на стороне базы. Нельзя полагаться только на скрытие кнопок или фильтрацию данных в интерфейсе.

## 4. Предлагаемая модель данных

| Сущность | Назначение | Основные связи |
|---|---|---|
| profiles | Публичные настройки профиля пользователя | auth.users |
| studios | Студия или практика | владелец, участники |
| studio_memberships | Участие пользователя и роль | user ↔ studio |
| clients | Клиентская карточка | studio |
| client_notes | Рабочие заметки инструктора | client, studio, author |
| groups | Группы занятий | studio |
| group_members | Состав группы | group, client |
| exercises | Системный каталог упражнений | общие записи каталога |
| exercise_versions | Версии карточек упражнений | exercise |
| plans | План/комплекс занятия | studio, author |
| plan_items | Упражнения и порядок внутри этапов | plan, exercise |
| templates | Шаблоны занятий | studio, author |
| schedule_events | Запланированное занятие | studio, instructor, group/clients |
| attendance | Факт посещения | schedule_event, client |
| audit_events | Важные события доступа и изменения данных | studio, actor |

Это концептуальная схема, не готовая SQL-миграция. Точные поля, ограничения и индексы определяются при реализации после проверки сценариев.

## 5. Правила безопасности и приватности

1. В браузере хранить только публичный ключ клиента, предназначенный для безопасного использования с RLS; секретные service-role ключи и пароли не помещать в frontend, репозиторий или публичные файлы.
2. Каждая таблица с данными студии должна иметь studio_id и политики RLS для чтения/создания/изменения/удаления.
3. Серверные административные операции выполнять только в доверенной среде, не из браузера.
4. Проверять права не только при чтении, но и при записи, смене владельца и удалении.
5. Минимизировать данные клиентов: собирать только то, что действительно нужно для работы инструктора.
6. Не превращать заметки инструктора в медицинскую карту; не запрашивать диагнозы и не обещать клиническую оценку. Если позже появится работа с чувствительными данными о здоровье, до этого нужен отдельный юридический и security review.
7. Предусмотреть экспорт данных организации, удаление/закрытие аккаунта, политику хранения и резервное копирование.
8. Не хранить данные платёжных карт самостоятельно; платежи, если появятся, поручать специализированному провайдеру.
9. Вести минимальный журнал важных действий без избыточного копирования содержимого личных заметок.
10. Проверять RLS тестами на двух независимых студиях: пользователь студии A не должен прочитать или изменить данные студии B.

## 6. Переход с текущей локальной версии

Переход выполнять без внезапного удаления текущего локального механизма:

1. Зафиксировать формат текущего JSON backup как источник миграции.
2. Добавить слой repositories / data-adapters: LocalRepository для текущего хранилища и будущий CloudRepository.
3. Добавить экран входа и состояние сессии только после готовности Auth и RLS.
4. Для авторизованного пользователя читать и записывать облачные данные через репозитории.
5. Добавить явный мастер импорта существующего JSON в облачный аккаунт: предварительный просмотр, подсчёт записей, подтверждение, отчёт о пропусках и повторяемость без дублей.
6. Сохранить экспорт облачных данных в переносимом формате.
7. После проверки облачного сценария определить, оставить ли локальный режим как резервный/офлайн режим или убрать его из основного потока.

Не объединять автоматически локальные данные разных браузеров и аккаунтов. При конфликте данных нужен понятный выбор пользователя; молча перезаписывать записи запрещено.

## 7. Последовательность реализации

### Фаза 0 — проектирование (текущий этап)
- Зафиксировать облачную модель и multi-tenant подход.
- Согласовать границы клиентских данных и роли.
- Утвердить провайдера и регион размещения.
- Подготовить схему, угрозы и правила RLS.

### Фаза 1 — технический фундамент
- Создать отдельное окружение разработки и тестовую облачную базу.
- Настроить миграции схемы и безопасное хранение секретов.
- Реализовать Auth, профили, студии и членство.
- Написать и проверить RLS-политики до подключения интерфейса.
- Настроить резервное копирование и журналирование.

### Фаза 2 — первый вертикальный сценарий
- Вход/выход.
- Создание профиля и первой студии.
- Облачное сохранение и открытие одного занятия.
- Изоляция двух тестовых студий.
- Экспорт и восстановление тестовых данных.

### Фаза 3 — рабочие данные инструктора
- Облачная библиотека и версии упражнений.
- Шаблоны и история занятий.
- Импорт локальной резервной копии.
- Обработка сетевых ошибок и повторных запросов.

### Фаза 4 — клиенты и группы
- Карточки клиентов с минимальным набором полей.
- Группы и членство.
- Разграничение доступа по ролям.
- Экспорт и удаление данных клиента.

### Фаза 5 — расписание и операционная работа
- События календаря, повторяемость, часовые пояса.
- Посещаемость и переносы/отмены.
- Напоминания только после согласования канала и правил согласия.

### Фаза 6 — платформа
- Аналитика, отчёты, несколько студий на пользователя.
- Клиентский кабинет — отдельное решение.
- Платежи/подписки, интеграции и мобильные приложения — отдельные проекты после проверки спроса и экономики.

## 8. Критерии допуска к реальным данным

Не подключать реальные клиентские данные, пока не выполнено всё:
- RLS включён и проверен автоматическими негативными тестами.
- Нет секретных ключей в frontend или публичном репозитории.
- Проверены роли и границы доступа.
- Есть экспорт, резервное копирование и понятный сценарий восстановления.
- Есть политика конфиденциальности и описаны цели/сроки хранения.
- Есть процедура удаления аккаунта и данных.
- Проверены ошибки сети, повторная отправка и конфликты.
- Проведён ручной тест на двух отдельных аккаунтах/студиях.

## 9. Что не делать сейчас

- Не переносить существующие реальные записи и резервные копии в облако.
- Не создавать аккаунты клиентов и публичную регистрацию без готовых правил.
- Не добавлять медицинские поля «на всякий случай».
- Не связывать UI напрямую с таблицами провайдера.
- Не переписывать весь frontend до доказанной необходимости.
- Не включать платный тариф и не публиковать ключи/секреты без отдельной проверки.

## 10. Следующая точка согласования

Перед созданием облачного проекта и схемы, пригодной для реальных данных, требуется подтвердить два продуктовых правила:

1. **Кто будет входить в систему на первом облачном релизе?** Рекомендация: только инструкторы/владельцы студий и приглашённые сотрудники; клиенты пока остаются карточками без самостоятельного входа.
2. **Какие сведения хранить о клиенте?** Рекомендация для MVP: имя/отображаемое имя, контакт по необходимости, принадлежность к группе, посещаемость и нейтральные рабочие заметки. Не собирать диагнозы, медицинские документы и подробные сведения о здоровье.

До согласования этих правил допустимы проектирование, прототипирование и тестовые данные, но не сбор реальных клиентских данных.
